# Release Prep Prompts (v1)

> 目的：把你之前那两条“继续推进完整度 / 质量硬化”长指令，改成适配当前 **收尾发布准备** 阶段的可直接复制版本。
>
> 当前定位：主功能已基本落地；现在不再继续扩能力，也不再继续追纯行数瘦身，而是把默认分支、文档真相、发布矩阵、真实 smoke 和质量 gate 收成一个可宣告首版发布准备完成的状态。

## 1. 收尾发布准备（默认推进版）

适用：你希望 Codex 按当前主线自己推进，先收口文档真相和发布矩阵，再继续做首版发布准备所需的最小闭环。

```text
按 AGENTS.md + docs/STATUS.md + docs/NEXT_STEP.md + docs/DECISIONS.md + docs/ARCHITECTURE.md 执行。

当前进入“收尾发布准备阶段”：
暂时不继续新增用户可感知功能，不扩协议，不再追新的大文件瘦身数字；当前目标是把默认分支、文档真相、发布矩阵、真实 smoke 和质量 gate 收成一个可宣告首版发布准备完成的状态。

文档主要服务 Codex 连续施工，不以非技术操作者可读性为优先；文档只维护执行真相、当前状态、当前主线和长期边界，不做额外的人类入口优化。

本机真实测试环境按当前实际状态处理：
凡是任务需要真实 downloader / import / refresh 验证，直接执行，不要留给我；
但必须区分“代码回归”和“今天这台机器的环境未就绪”，不要把环境不可达直接写成业务回归。

默认连续执行 3 轮；每轮只做一个最小闭环，自己完成：实施、验证、必要时更新文档、review diff、commit 并 push。

当前阶段固定目标，不要偏离：
1. 默认分支持续可用，现有全量回归与 focused tests 不回退
2. docs/STATUS.md、docs/NEXT_STEP.md、operator prompts 与当前代码/验证真相保持一致
3. 先冻结首版发布矩阵，再围绕矩阵内能力补 live smoke 和发布前质量 gate
4. 不把“代码里已有实现”直接等同于“首版发布承诺”
5. 不用顺手加功能来掩盖收尾定义和发布准备问题

当前阶段优先按这个顺序选闭环：
1. 先修当前文档真相漂移
2. 再明确首版发布矩阵（渠道、下载器、真实链路）
3. 再补首版矩阵内的最小真实 smoke / 发布前验证
4. 再补发布前质量 gate
5. 只有以上方向都没有更小闭环可做时，才处理次级结构债

执行约束：
6. 每轮只选一个最小闭环，不做大杂烩
7. 不新增功能，不改对外协议，不改 SQLite 真相边界，除非该修改是修复当前发布前回归或收口发布矩阵所必需
8. 优先做“能提高首版发布确定性”的改动，而不是表面整洁
9. 每轮必须自己验证；需要真实验证就直接跑，不要留给我
10. 文档只同步当前发布准备真相，不写长篇总结，不把历史台账抄回 STATUS

如果某一轮结束后没有立刻看到下一步，不允许直接停止；先重新扫描 docs/STATUS.md、docs/NEXT_STEP.md、相关代码、失败测试、最近提交和当前发布矩阵，再从当前主线缺口、当前发布前风险或当前环境真相里选一个更小、更保守的闭环继续做。

只有在以下情况才允许停止：
11. 明确 blocker
12. 明确达到 docs/NEXT_STEP.md 当前主线 Done when 的任一可测量退出条件
13. 触发 AGENTS.md §11 的诊断分流递减停机线
14. 继续修改会违反 AGENTS.md 或当前文档边界
15. 无法确认 commit / push 状态

默认不要中途汇报。只有在以下情况才汇报：
16. 失败
17. 遇到 blocker
18. 必须由我决定
19. 触发诊断分流递减停机线

全部轮次结束后，只做一次简短总结，输出：
20. 当前主线完成度
21. 默认分支当前质量状态
22. 本次完成的发布准备闭环
23. 首版发布矩阵还差什么
24. 最后停下来的原因
```

## 2. 收尾发布准备（保守质量优先版）

适用：你想让 Codex 用更保守的方式连续施工，优先把发布口径、质量入口和真实验证收死，不急着追完整支持矩阵。

```text
按 AGENTS.md + docs/STATUS.md + docs/NEXT_STEP.md + docs/DECISIONS.md + docs/ARCHITECTURE.md 执行。

当前进入“收尾发布准备阶段（保守质量优先版）”：
暂时不继续推进项目完整度，不新增用户可感知功能，不扩协议，不追新能力；当前目标是持续降低“发布口径不清、文档漂移、环境真相不明、发布前验证不完整”这些收尾风险，把默认分支提升到可宣告首版发布准备完成的状态。

文档主要服务 Codex 连续施工，不以非技术操作者可读性为优先；文档只维护执行真相、当前状态、当前发布结论和长期边界，不做额外的人类入口优化。

本机真实测试环境按当前实际状态处理：
凡是任务需要真实 downloader / import / refresh 验证，直接执行，不要留给我；
但必须把“代码问题”和“当前机器环境不可达”分开记录，不允许再把环境问题写成旧业务黄灯。

默认连续执行 8 轮；每轮只做一个最小闭环，自己完成：实施、验证、必要时更新文档、review diff、commit 并 push。

当前阶段固定目标，不要偏离：
1. 默认分支现有回归和质量入口持续收绿，不能接受当前真相继续漂移
2. 首版发布矩阵先冻结，再讨论是否恢复完整支持矩阵推进
3. 真实 smoke 只围绕首版承诺范围补，不搞无限扩表
4. 文档、operator prompt、README/入口说明与当前代码真相保持一致
5. 新增或调整发布前质量 gate，让后续回归更早暴露
6. 不用“顺手加功能”来掩盖收尾问题

当前阶段重点债务，优先按这个方向选闭环：
1. 先修当前文档与验证真相不一致
2. 再冻结首版发布矩阵
3. 再补首版矩阵内的最小真实 smoke
4. 再补强 Makefile / CI / lint / static check 等发布前质量入口
5. 只有在以上方向都没有更小闭环可做时，才处理次级结构债

执行约束：
7. 每轮只选一个最小闭环，不做大杂烩
8. 不新增功能，不改对外协议，不改 SQLite 真相边界，除非该修改是修复当前发布前回归所必需
9. 优先做“能提高首版发布确定性”的改动，而不是继续磨已达标壳文件
10. 每轮必须自己验证；需要真实验证就直接跑，不要留给我
11. 文档只同步当前发布真相，不写长篇总结，不把历史台账抄回 STATUS

如果某一轮结束后没有立刻看到下一步，不允许直接停止；先重新扫描 docs/STATUS.md、docs/NEXT_STEP.md、相关代码、失败测试、最近提交和当前发布矩阵，再从当前发布前风险、当前主线缺口或当前环境真相里选一个更小、更保守的闭环继续做。

只有在以下情况才允许停止：
12. 默认分支已恢复稳定，且当前这轮已完成一个可验证的发布准备闭环
13. 触发 AGENTS.md §11 的诊断分流递减停机线
14. 继续修改会违反 AGENTS.md 或当前文档边界
15. 无法确认 commit / push 状态

默认不要中途汇报。只有在以下情况才汇报：
16. 失败
17. 遇到 blocker
18. 必须由我决定
19. 触发诊断分流递减停机线

全部轮次结束后，只做一次简短总结，输出：
20. 默认分支当前质量状态
21. 当前最大剩余发布前风险
22. 本次完成的发布准备闭环
23. 是否已可以进入“首版发布准备完成”判定
24. 最后停下来的原因
```

## 3. 现在怎么用

- 想让 Codex 按当前主线正常推进：用上面的“收尾发布准备（默认推进版）”
- 想更保守地先把发布口径、质量入口和真实 smoke 收死：用上面的“收尾发布准备（保守质量优先版）”
- 如果只想要更短的可复制入口，继续看 `docs/OPERATOR_RUNBOOK.md`
