## 1. 问题从何而来

这个项目的起点不是“做一个通用 AI 平台”，而是一个很具体的个人观影痛点：

- 想要一个像聊天一样下命令的入口
- 想要从“找片 -> 选资源 -> 下载 -> 入库 -> 刮削 -> 字幕 -> 刷新 -> 通知”尽量自动打通
- 想让 Telegram 这种即时对话体验替代手动开很多网页和面板

更早期的理想形态其实比现在大得多：

- Telegram
- 企业微信
- 个人微信
- 飞书
- PT / BT 分流
- 全自动字幕
- 媒体库删除后的源文件联动清理
- 通知和统计

但项目很快就遇到一个现实问题：

- 想做的东西很多
- 真正会改文件、改下载器状态、改数据库状态的动作风险很高
- 如果一开始同时做多渠道、多下载器、多自动化、外站抓取、清理联动，项目会先乱掉，而不是先跑起来

所以路线后来被强行收窄。

## 2. 路线为什么会收窄

项目演变过程中，最重要的一次转向不是“功能加了什么”，而是“边界被重新画清楚了”。

### 早期大方向

最早的理想型是一个多渠道、全流程、对话式影视自动化系统。

它想解决的是：

- 入口太多太散
- 手工搜资源太慢
- 下载和入库链路太碎
- 字幕、刮削、刷新要手工收尾

### 后来的收窄原则

后面逐步形成了现在这套更现实的原则：

1. 先做单入口  
   先只认 Telegram 私聊，别同时做飞书、企业微信、微信。

2. 先做单主线  
   先把最窄的影视主链跑通，再谈大而全。

3. 先保住副作用边界  
   下载、导入、复制、刷新都必须先过审批，不能让模型直接拍脑袋执行。

4. 先把“真相”落到 SQLite  
   不能依赖聊天记录记住任务状态。

5. 先把 PT 和 BT 入口分开  
   正常观影需求和直接 BT 下载需求不是一回事，必须从入口就分叉。

6. 不做通用平台化  
   不把项目带成通用 Agent 平台、通用 skill 平台、通用 scheduler 平台。

这次收窄，决定了 Luminarr 最终长成“一个窄而稳的垂直自动化 Harness”，而不是“什么都能做一点的平台”。

## 3. 关键演变过程

下面这条线，基本就是项目从“想法”走到“现在能跑”的过程。

### 阶段 A：最小观影主链

这一阶段主要补的是“能不能从聊天走到下载和导入”。

落地结果：

- Telegram 运行时
- TMDB-first 搜索
- 候选选择
- 下载器投递
- `status`
- `import`
- Emby refresh

这一阶段解决的是“最小闭环有没有”。

### 阶段 B：控制层补强

项目很快暴露出第二类问题：不是“功能没有”，而是“执行不稳”。

典型问题：

- Telegram 更新可能重复
- `confirm` 可能重复点、过期点、重启后重放
- 任务执行依赖聊天上下文，进程一重启就容易乱
- 模型异常会把用户链路搞断

后来的解决方式：

- `telegram_updates` 做去重真相源
- `jobs.version + lease_owner + lease_until` 做最小执行所有权
- `approval_record` 做 pending / approved / expired 真相
- `confirm` 改成从持久化 truth 重建执行上下文
- clarification pending 改成 SQLite 持久化
- 物理异常改成同轮压缩重试 + 安全文案

这一阶段解决的是“系统能不能稳住，不靠聊天记忆瞎扛”。

### 阶段 C：媒体后半段补齐

当“搜索 -> 下载 -> 导入”能跑后，问题又变成：

- 文件名乱
- 刮削信息不全
- 字幕要手工处理
- Emby 里虽然有文件，但体验不完整

后来的补法是：

- confirmed import 后做 deterministic rename
- metadata scraping 接 TMDB + Fanart.tv
- subtitle auto-translation 接专业模型翻译现成 `.srt`
- 最后接 Emby refresh

这一阶段解决的是“入库后不是只有一个文件，而是有可直接看的媒体形态”。

### 阶段 D：PT / BT 分流

再往后，项目发现一个越来越明显的问题：

- 正常观影需求和直接 BT 下载不是一回事
- 如果两条路混在一起，后面越做越乱

所以后来把 PT / BT 从入口拆开了：

- PT 主干：正常观影需求
- BT 主干：直接 `magnet:?` 或明确 BT 下载需求

然后又继续拆：

- BT 分类：`movie / series / anime / raw_bt`
- 媒体型 BT：继续走 TMDB、命名、刮削、字幕、刷新
- `raw_bt`：只做下载和放置，不进媒体链

这一阶段解决的是“别再把两类需求搅在一起”。

### 阶段 E：多下载器与 BT 订阅

再后面的问题是：

- 下载器不能只假设一个
- BT 需要持续扫描，不只是手动下一次

所以后来补了：

- downloader instance + role binding
- qBittorrent 最小协议执行
- `btsub` 手动基线
- `btsub` 最小后台 tick

这一阶段解决的是“BT 不只是一次性动作，而开始具备持续跟踪能力”。

## 4. 一些重要的“路线变化”

这部分是最值得回看的，因为它解释了为什么很多路后来没继续走。

### 从“多渠道并行”改成“Telegram 单入口先跑通”

变化前：

- 想同时做 Telegram、企业微信、微信、飞书

变化后：

- 当前唯一入口先固定为 Telegram 私聊

原因：

- 入口越多，调试面越大
- 控制层还没稳时，多入口只会把问题放大

### 从“能执行就行”改成“所有副作用都必须审批”

变化前：

- 选择后直接投递下载、直接导入的冲动很强

变化后：

- downloader / import 都必须先 pending，再 `confirm`

原因：

- 真实文件和下载器状态一旦被改，回滚成本很高

### 从“靠聊天上下文记住任务”改成“靠数据库记住真相”

变化前：

- 很多上下文只存在内存或聊天里

变化后：

- 关键任务状态都进 SQLite

原因：

- 重启后如果状态丢了，系统会开始乱做事

### 从“BT 只是另一种下载方式”改成“BT 是一条独立支线”

变化前：

- 容易把 BT 临时接进 PT 主链

变化后：

- BT 从入口开始独立
- `raw_bt` 与媒体型 BT 再继续分开
- 后续原始磁力入口还要继续细分成：
  - 影视入库链
  - 纯 BT 下载链

原因：

- 资源分类、后处理、目标目录都不一样

### 从“可能做 skill 平台”改成“只允许 BT 支线局部 helper”

变化前：

- 一度会往“通用 skill / plugin 平台”方向想

变化后：

- 正式规则明确不做通用平台化
- 只允许：
  - BT 外部网站源
  - 项目内站点规则文件
  - BT-only read-only helper

原因：

- 需要的是“把 BT 资源接进现有链路”，不是做一个通用能力市场

### 从“纯 BT 也许沿用影视规则”改成“纯 BT 只做单片优选”

变化前：

- 容易把 pure BT 也拉去复用影视资源那套复杂优选和后处理逻辑

变化后：

- pure BT 明确不走影视规则
- pure BT 更接近“单片资源版本优选”
- 后续允许“确定性预过滤 + LLM 辅助优选”

原因：

- 纯 BT 的目标不是入库成标准影视资料，而是挑出一份更出色的单片版本

## 5. 典型问题是怎么被解决的

这部分不是按功能分，而是按“遇到什么坑、后来怎么补”来写。

### 问题 1：重复更新和重复执行

现象：

- Telegram 更新可能重复送达
- 同一个 `confirm` 可能被重复触发

解决：

- `telegram_updates` 去重
- `approval_record + jobs` 防重放
- `lease_version / executed_version` 拦 stale confirm

### 问题 2：进程一重启，上下文容易丢

现象：

- clarification pending 丢失
- BT follow-up 丢失
- pending approval 唤醒后容易靠旧聊天猜上下文

解决：

- clarification truth 持久化
- BT pending truth 持久化
- confirm wake 只从持久化 truth 重建

### 问题 3：导入动作很危险

现象：

- 误导入、重复导入、跨文件系统失败都很麻烦

解决：

- import approval
- hardlink 默认
- cross-filesystem 进入 copy-fallback pending
- 不静默降级为 copy

### 问题 4：下载完成后自动化不够闭环

现象：

- 需要手工查状态
- 需要手工再触发导入

解决：

- completion-monitor
- observed complete -> auto import pending
- 但仍保留 `confirm`

### 问题 5：资源质量太差也会被推进

现象：

- 明显低质量片源也可能继续走自动链

解决：

- 最小 deterministic 低质量规则门
- 命中 `CAM / TS / SCR / WORKPRINT` 就停止自动推进

### 问题 6：BT 与 PT 混用导致链路混乱

现象：

- 直接磁力、普通观影搜索、原始 BT 文件需求搅在一起

解决：

- PT / BT parser-level split
- BT classification
- `raw_bt` 与媒体型 BT 分开

### 问题 7：BT 需要更多来源，但又不能污染 PT

现象：

- 只靠 Prowlarr 不一定够
- 但如果直接引入通用 skill 平台，会把项目带偏

解决方向：

- 后续允许 `WebSource`
- 后续允许项目内站点规则文件
- 后续允许 BT-only read-only helper
- 但都只长在 BT 支线

### 问题 8：原始磁力虽然天然是 BT，但后续处理链并不只有一种

现象：

- 用户发的都是 `magnet:?`
- 但有的其实想走影视入库链
- 有的只是想走纯 BT 下载链

解决方向：

- 不再从用户视角重复问“PT 还是 BT”
- 改成问“影视入库链还是纯 BT 下载链”
- 让后面的处理方式分清楚

### 问题 9：纯 BT 的“最好版本”不适合照搬影视规则

现象：

- pure BT 资源不一定是标准影视资料
- 目标也不是做 TMDB / metadata / subtitle / refresh

解决方向：

- pure BT 按单片资源逻辑处理
- 先用代码做基本过滤
- 再允许 LLM 辅助挑更好的版本

## 6. 当前项目到了什么程度

如果用很直白的话说：

- **不是原型玩具了**
  因为控制层、审批、重启后恢复、下载与导入边界都已经补上了。

- **也还不是完全成熟产品**
  因为多渠道、外站抓取、字幕提取、联动清理、通知统计、全局调度都还没做完。

更准确一点，可以这样理解：

- **控制层成熟度：中高**
  已经有去重、审批、lease、重建、恢复边界。

- **媒体主链成熟度：中高**
  搜索、下载、导入、命名、刮削、字幕、刷新都已经打通。

- **BT 主链成熟度：中**
  已经有分流、分类、TMDB 关联、raw_bt 目录、qB、`btsub`、后台 tick。
  但 BT 选源、外部站点、helper 还没继续补。

- **渠道成熟度：中低**
  代码里已经有 Telegram / personal WeChat / Feishu / WeCom 四个私聊入口；
  但当前保守首版发布承诺矩阵仍只冻结为 Telegram 私聊。

- **运维自动化成熟度：低到中**
  还没补 downloader/library 关联清理，也还没补通知统计主线。

所以目前最准确的判断是：

**Luminarr 已经从“想法”进化成“能稳定跑主链的窄系统”，但距离“你最初设想的全渠道、全自动、全联动形态”还有明显几段路。**

## 7. 现在的正式口径

当前正式口径可以压缩成下面这几句话：

- 代码里当前已有 Telegram / personal WeChat / Feishu / WeCom 四个私聊入口。
- 但当前保守首版发布承诺矩阵仍只冻结为 Telegram 私聊。
- 当前最近一步是 BT subscription deterministic candidate-selection baseline。
- 原始磁力后续会增加“影视入库链 / 纯 BT 下载链”问询。
- pure BT 后续按单片资源优选，不复用影视入库链的复杂规则。
- 后续 BT 允许增加外部网站源。
- 后续 BT 允许增加 BT-only read-only helper。
- 但项目仍然不做通用 skill / plugin / MCP 平台。

## 8. 这份文档该怎么用

适合在这些场景看：

- 新开一个长任务前，先快速理解项目来龙去脉
- 发现“为什么规则这么保守”时，回来看历史原因
- 想判断某个新功能该放 PT 还是 BT、该放现在还是后面时，先对照这里的演变路径

不适合在这些场景用：

- 判断当前 step 到底做什么  
  这个看 `docs/NEXT_STEP.md`

- 判断当前什么已经落地  
  这个看 `docs/STATUS.md`

- 判断规则冲突到底谁说了算  
  这个看 `docs/DECISIONS.md`
