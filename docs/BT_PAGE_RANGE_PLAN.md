# BT page / range plan (v1)

> 目的：把 BT 从“只支持关键词批量预览”推进到“能接确定性用户页 / 列表页 / 编号范围页输入”，同时继续复用既有 approval -> confirm -> jobs 真相边界。

## 1. 为什么现在切回 BT

- 2026-04-19 已确认当前主机没有可达 Plex 实例，Plex 真实 refresh smoke 值得性重评估按“暂不继续追 Plex，先回到 BT 更大范围能力”收口。
- 现有 BT 链已经有 `bt搜` 和 `bt批量 / bt批量确认`，但它们仍主要围绕“关键词搜到的一页结果”工作。
- 真正缺的更大能力是：用户已经拿到一个受控站点页面时，系统还不能把这个页面里的候选确定性预览出来，更不能用现有编号范围把它收进既有确认链。

## 2. 当前最小闭环

当前先只收一个更保守的入口：

1. 用户发送 `bt批量 <allowlist 页面 URL> 1-3`；
2. parser / routing 明确识别这不是普通关键词，而是 BT allowlist 页面请求；
3. 确定性代码只接受当前站点规则里已声明的页面类型，例如用户页 / 列表页；
4. 站点页抓取成功后，继续复用现有去重、编号范围过滤、批量预览文本和候选缓存；
5. 后续 `bt批量确认 1-3` 仍复用既有单条 approval / confirm / jobs 边界，不自动 `confirm`。

当前第一步不做：

- 不让 LLM 决定该抓哪个 URL
- 不接未声明站点
- 不在这一步直接批量 dispatch
- 不把 PT 主链或媒体型 BT 入库链一起放宽

## 3. Phase 顺序

1. Phase 1：补 allowlist 页面 URL 识别、页面类型校验、只读批量预览。
2. Phase 2：在已有页面直链站稳后，再补更省输入的页码 / 编号范围语法糖。
3. Phase 3：如果后续还要补更多站点或页面类型，再单独扩站点规则，不在这一条里顺手平台化。

2026-04-19 当前进度：

- Phase 1 的页面 URL 识别、页面类型校验和只读批量预览已落地；
- `bt批量 <allowlist 页面 URL> 1-3` 现在会走 allowlist 页面抓取，不再误落回关键词搜索；
- 未声明页面会显式回中文拒绝，不会静默去抓未知站点；
- 页面预览的聊天候选缓存和 Telegram 路由证明也已补齐；
- 当前剩余最小缺口是：把“页面预览出来的候选继续走 `bt批量确认`”这条复用关系补成更直接的 focused proof。

## 4. Done when

当前主线视为 **已收口**，满足以下任一条即可：

1. `bt批量 <allowlist 页面 URL> 1-3` 已能返回只读批量预览，并且候选可继续被 `bt批量确认` 复用进现有下载确认链；对应 focused tests 全绿；
2. 已明确证明当前 allowlist 页面输入还缺哪个确定性边界，并把 fail-closed 中文拒绝、处理建议和 focused tests 补齐；
3. 本轮代码变更 `< 20` 行且只是对同一个 page/range helper 再补一条 `if/elif/log` 诊断分支，触发 `AGENTS.md §11` 停机规则。

## 5. 不做清单

- 不做自动 `confirm`
- 不做未知站点 / 动态站点 / CAPTCHA / 登录态页面
- 不把这一步扩成通用插件平台
- 不改现有 downloader approval / confirm / lease/version / SQLite 真相边界
